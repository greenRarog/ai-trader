# AI Trader — Sandbox и экономный анализ ИИ

Go CLI: рыночные данные T-Invest Sandbox → решение Codex/OpenAI → Risk Engine →
отдельно вызываемый исполнитель Sandbox-заявок. PostgreSQL хранит контекст,
решения, капитал, денежные потоки, намерения и историю состояний заявок.
Реального торгового контура и вывода денег в приложении нет.

## Обновление существующего проекта

```sh
cd /home/green/git/ai-trader
docker compose --profile test run --rm --build tests
bash scripts/build-local.sh
docker compose up -d --wait postgres
bash scripts/trader.sh db migrate
bash scripts/trader.sh trading status
```

Миграции v4–v5 сохраняют предыдущие данные, добавляют журналы исполнения,
денежных потоков, лимит вызовов ИИ и сохранённые окна анализа. Имеющаяся
инициализация и состояние паузы сохраняются; новый счёт по умолчанию на паузе.
Имеющиеся 100 000 виртуальных ₽ повторно пополнять не нужно.

Go на хосте не требуется: Docker экспортирует статический Linux-бинарник и
bundle CA в `bin/`. Launcher работает под пользователем, выполнившим
`codex login`, использует `.env` и PostgreSQL Unix-сокет `.runtime/postgres`.
`trader.sh` запускайте без sudo. Данные БД находятся в `postgres_data`, а не в
каталоге сокета. Обычный `docker compose down` сохраняет данные; `down -v` удаляет их.

## Экономия токенов и автоматический анализ (v5)

По умолчанию не более **двух попыток обращения к модели в московский день**
на счёт, суммарно по провайдерам и моделям. Ошибка, таймаут или падение процесса
после резервирования попытки тоже расходуют лимит: приложение не может доказать,
что запрос не дошёл до модели. Внутренние сетевые повторы самого Codex этот
счётчик не различает. Смена модели или перезапуск приложения лимит не сбрасывают.
Старые вызовы до v5 не имеют маркера попытки и не входят в новый лимит.

```sh
# Обычный анализ с локальными проверками, кэшем и дневным лимитом:
bash scripts/trader.sh analyze
# Явно разрешить ещё одну попытку, обходя кэш и дневной лимит:
bash scripts/trader.sh analyze --refresh
# Только просмотр компактного входа, без ИИ и без расходования лимита:
bash scripts/trader.sh market --compact
# Отчёт по фактическому usage за московские календарные дни:
bash scripts/trader.sh usage --days 7
```

`--refresh` не обходит паузу, проверку данных, доступности торгов и Risk Engine.
Если рынок закрыт, котировки устарели, нет завершённых часовых свечей, состояние
счёта некорректно или для всех кандидатов запрещены и покупка, и уменьшающая
позицию продажа, вызова модели не будет. Go проверяет минимальный лот через
тот же Risk Engine; это проверка возможности сделки, а не выбор BUY/SELL.
При стопах покупки фильтруются, допустимые уменьшающие продажи сохраняются.
Результат `skipped` с локальным HOLD и причинами записывается в историю.

Модель получает нормализованный баланс и позиции без полных дублирующихся
`positions`/`portfolio`, идентификаторов счёта и служебных полей. Деньги — точные
десятичные строки RUB, свечи — компактные кортежи OHLCV; все выбранные свечи и
пять уровней стакана сохраняются. Календарь сокращён до текущего дня. Ограничения,
свежесть источников и показатели риска сохраняются. Полный снимок остаётся в БД.
`market --compact` показывает формат до фильтрации и добавления истории капитала.

Codex запускается отдельной новой сессией во временном каталоге, без контекста
репозитория, старого диалога, пользовательского конфига и проектных AGENTS.md.
Встроенные инструкции разработчика заменяются короткими торговыми через
[`model_instructions_file`](https://learn.chatgpt.com/docs/config-file/config-reference).
Ограничения на инструменты и окружение остаются. Настройки глобального Codex
не изменяются. Сервер/модель могут добавлять свои накладные расходы — сравниваем
реальный `usage`, не выдаём длину текста за точное число токенов.

Повтор идентичного контекста в пределах `AI_CACHE_TTL` (по умолчанию 10 минут)
использует исходный результат с `status=reused`, без нового вызова и без
дублирования usage. Учитываются исходные времена цен/стакана/свечей, состояние
портфеля, ограничения и стопы. Время сбора снимка и счётчик замеров не влияют на
ключ. Перед повторным использованием данные и предложение проверяются заново.
Ранее неуспешная/неопределённая попытка автоматически не повторяется в этот срок.
`reused` не создаёт новую исполняемую рекомендацию: `economy.reused_from`
указывает исходный analysis ID; для него действуют прежний срок 10 минут,
уникальность намерения и свежая проверка перед исполнением.

`economy` в результате содержит размеры полного снимка, компактного входа и
запроса **в байтах**, маркер попытки, причины фильтрации/пропуска и ссылку на
исходный анализ. `usage` группирует реальные входные/выходные/cached токены,
попытки, пропуски и повторное использование по дню, провайдеру и модели.
Cached-токены входят во входные, их не следует прибавлять повторно. Отсутствие
usage означает неизвестный расход. Долларовую стоимость подписки не выдумываем;
тарифную оценку для API можно добавить отдельно.

### Запуск по двум дневным окнам

```sh
# Один проход без постоянного процесса (в выходной ожидается idle):
bash scripts/trader.sh automation tick
# Постоянный процесс, остановка Ctrl+C:
bash scripts/trader.sh automation run
```

Команда `automation run` работает пока запущена. Пользовательские службы
и таймеры устанавливает `python3 scripts/install-services.py`. Codex запускается на хосте с
существующим ChatGPT login; его OAuth-файлы в контейнер не монтируются.

Раз в минуту сервис проверяет состояние. Для инициализированного счёта сверяет
деньги/акции и читает незавершённые заявки; при позициях или восстановленных
заявках сохраняет замер капитала. Это не вызывает ИИ. Неопределённые заявки
только опрашиваются, POST не повторяется. Несоответствие учёта или достижение
наблюдаемого лимита потерь ставит счёт на паузу; принудительной продажи нет.

Два 30-минутных окна определяются по главной сессии MOEX из API: через час
после открытия и за час до закрытия. Вне окон, в аукцион/клиринг или без
проверенного расписания модель не вызывается. Вечерняя/дилерская сессия не
создаёт дополнительных окон. Слишком короткая основная сессия (<3 часов)
пропускается. Пропущенное окно не догоняется.

Попытка окна записывается в PostgreSQL **до** сбора данных и вызова модели.
Перезапуск и параллельный процесс не повторяют это окно, даже при ошибке.
Пропуск по данным тоже завершает попытку окна; ручной анализ доступен отдельно.
Дневной лимит общий с ручным `analyze`. Пока торговля на паузе, окна не
расходуются. Для включения анализа используется прежний `trading resume`.

При `AUTOMATION_EXECUTE_ORDERS=false` автоматический режим только анализирует.
При `true` он исполняет свои свежие прошедшие проверки BUY/SELL, повторно
проверяя риск и состояние счёта перед отправкой. HOLD, кэш/reused и ручные
анализы автоматически не исполняются. Пополнения и снятие паузы остаются ручными.
Результаты старше 10 минут не исполняются. Признак `automatic_execution`
сохраняется до обращения к ИИ; свежий результат или подготовленное намерение
восстанавливаются после перезапуска. `submitting`/`unknown` только сверяются,
без повторного POST. При отключении настройки новая автоматическая отправка
прекращается, сверка уже отправленных заявок продолжается даже на паузе.

Явный разовый запуск вне дневного окна: `automation tick --now`. Он сохраняет
дневной лимит, кэш и все проверки, а при включённой настройке может отправить
Sandbox-заявку. Непрерывная служба не использует `--now`.

## Первый Sandbox-цикл

Сначала включите контроль выделенного виртуального счёта. Первый запуск
принимает только счёт с положительными рублями, без акций и активных заявок:

```sh
bash scripts/trader.sh trading resume
bash scripts/trader.sh market
bash scripts/trader.sh analyze --instruments SBER:TQBR,GAZP:TQBR
bash scripts/trader.sh history --limit 10
```

`trading resume` фиксирует исходные деньги для последующей сверки. Повторный
resume не переопределяет исходный остаток и не снимает стопы по потерям.
`analyze` по-прежнему **никогда не выставляет заявку**.

Если ИИ вернул свежий BUY/SELL, который прошёл проверки, можно отдельно исполнить
его по UUID анализа:

```sh
bash scripts/trader.sh orders execute --analysis UUID_АНАЛИЗА
bash scripts/trader.sh orders list
```

Это команда, которая действительно отправляет виртуальную заявку брокеру.
HOLD, отклонённые решения и анализ старше 10 минут исполнять нельзя.
Обычная команда также отклоняет ручные `risk-check`.
В закрытую или дилерскую сессию ожидается локальный `skipped` без вызова ИИ;
не подменяйте решение ИИ вручную ради прохождения проверки.

Для явно выбранного владельцем теста исполнения в Sandbox предусмотрен отдельный
флаг. Он принимает свежий успешный `risk-check` ровно на один лот и сохраняет
происхождение `manual_check`; решение не выдаётся за рекомендацию ИИ:

```sh
bash scripts/trader.sh risk-check --action BUY --instrument SBER:TQBR --lots 1
bash scripts/trader.sh orders execute --analysis UUID_ПРОВЕРКИ --sandbox-test
# После подтверждённой покупки подготовить новую проверку SELL и исполнить её:
bash scripts/trader.sh risk-check --action SELL --instrument SBER:TQBR --lots 1
bash scripts/trader.sh orders execute --analysis UUID_ПРОВЕРКИ_SELL --sandbox-test
```

Каждая команда `orders execute` действительно отправляет Sandbox-заявку.
Пауза, свежая проверка рисков, сверка учёта, журнал и идемпотентность действуют
в тесте так же, как при исполнении рекомендации ИИ.

Заявка лимитная, с `TIME_IN_FORCE_FILL_AND_KILL`, без согласия на маржинальную
сделку. Цена покупки округляется вниз к шагу цены, продажи — вверх. Неисполненный
остаток должен отменяться согласно алгоритму брокера; состояние всё равно
проверяется через API. Sandbox использует упрощённое исполнение и не воспроизводит
реальную ликвидность.

## Идемпотентность и восстановление заявок

Перед запросом брокеру в БД создаётся намерение с UUID. Этот же UUID передаётся
как `orderId` — ключ идемпотентности. На один analysis ID допускается только одно
намерение, включая неуспешные/отменённые результаты.

Последовательность: `prepared` → сохранённые свежие request/snapshot/risk →
`submitting` → `acknowledged` → `active`/`partial` либо конечное состояние
`filled`/`cancelled`/`rejected`. Отказ до отправки даёт `blocked`.

```sh
bash scripts/trader.sh orders list --id UUID_НАМЕРЕНИЯ
bash scripts/trader.sh orders events --id UUID_НАМЕРЕНИЯ
bash scripts/trader.sh orders reconcile
bash scripts/trader.sh orders reconcile --id UUID_НАМЕРЕНИЯ
bash scripts/trader.sh orders cancel --id UUID_НАМЕРЕНИЯ
```

При потере ответа остаётся `submitting` или `unknown`. Повтор `orders execute`
для того же анализа выполняет поиск исходной заявки; **POST повторно не отправляется**.
Если биржевой ID неизвестен, поиск идёт по сохранённому ключу запроса через
`ORDER_ID_TYPE_REQUEST`. Ответ «не найдено» не доказывает отсутствие заявки и
не разрешает повторную отправку. Неопределённый результат блокирует следующие
операции по счёту. Полное автоматическое восстановление невозможно, если брокер
уже удалил историю состояния: потребуется разбор владельцем.

Частичные исполнения хранятся накопительно, а не суммируются при каждом опросе.
Проверяются идентичность заявки, отсутствие уменьшения исполненного количества,
ценовой лимит и фактическая комиссия. Каждый ответ состояния сохраняется до
финансовой проверки. Неожиданные данные сохраняются для разбора и блокируют
продолжение. Известные ответы InvalidArgument/Unauthenticated/PermissionDenied
при POST считаются отказом; сетевые ошибки остаются неопределёнными.

`orders reconcile` без ID обходит незавершённые намерения. С ID можно обновить
также конечный результат, например после позднего уточнения комиссии. У брокера
есть ограничение хранения состояний; локальный журнал хранится независимо.

## Сверка денег и позиций

Счёт предназначен для управления этим приложением. Ожидаемые деньги считаются
от исходного остатка плюс подтверждённые внешние потоки и фактические денежные
эффекты собственных исполнений. Количество акций считается по исполненным
лотам и сохранённой лотности. Перед заявкой и после конечного исполнения эти
значения сверяются с брокером. Необъяснимые изменения останавливают продолжение.

Внутри приложения операции счёта сериализованы advisory lock. Перед POST
дополнительно транзакционно блокируется строка управления счётом: потеря
сессии advisory lock не даёт двум подготовленным заявкам одновременно пройти
барьер отправки. Незавершённое пополнение или заявка блокируют новые мутации.

Расчёт исполненного денежного эффекта использует наблюдаемое поведение Sandbox:
`totalOrderAmount` — сумма сделки, `executedCommission` — отдельная комиссия.
BUY списывает `total + fee`, SELL зачисляет `total - fee`. Покупка/продажа SBER
26 октября 2026 подтвердили это точной сверкой баланса; на первый неверный
расчёт комиссии сработала постоянная пауза. Данные API сохраняются в журнале.

При изменении поведения Sandbox сверка остановит следующие заявки.
Частичное исполнение и сетевые сбои на работающем Sandbox требуют отдельных
испытаний; проверка двойниками брокера не заменяет их.

## Пауза и отмена

```sh
bash scripts/trader.sh trading pause
bash scripts/trader.sh trading status
# После сверки/устранения причины:
bash scripts/trader.sh trading resume
```

Пауза сохраняется в PostgreSQL и запрещает прохождение новых заявок через
барьер отправки. Уже отправленный или находящийся в полёте запрос может
исполниться; для активной заявки есть отдельная команда `orders cancel`.
Пауза доступна без токена брокера. `resume` не очищает журнал и стопы риска.

## Денежные потоки и пополнения

`SandboxPayIn` не имеет нашего ключа идемпотентности на стороне брокера.
Теперь намерение пополнения записывается **до** запроса, а подтверждённое
пополнение атомарно попадает в журнал денежных потоков:

```sh
# Выполнять только если действительно нужно ДОБАВИТЬ виртуальные деньги:
bash scripts/trader.sh account fund --amount 1000 --confirm --id ВАШ_UUID
bash scripts/trader.sh cashflow funding
bash scripts/trader.sh cashflow list
```

UUID можно получить командой `python3 -c 'import uuid; print(uuid.uuid4())'`.
Без `--id` приложение генерирует и печатает UUID перед отправкой. Повтор с тем
же ID только возвращает сохранённое состояние и никогда не вызывает PayIn ещё
раз. Новый ID означает новое пополнение. После ошибки не создавайте новый ID,
пока не разобран исходный запрос.

При неопределённом исходе владелец сверяет баланс, затем явно отмечает результат:

```sh
bash scripts/trader.sh cashflow funding --id UUID_ПОПОЛНЕНИЯ
# Только после подтверждения, что деньги действительно зачислены:
bash scripts/trader.sh cashflow confirm --id UUID_ПОПОЛНЕНИЯ
# Или после подтверждения, что запрос НЕ применился и баланс остался прежним:
bash scripts/trader.sh cashflow abandon --id UUID_ПОПОЛНЕНИЯ
```

Обе команды проверяют ожидаемый остаток. Если отменённое локальное намерение
позже всё же зачислится у брокера, сверка обнаружит лишние деньги и заблокирует
новую торговлю. `abandon` не отменяет запрос у брокера и не разрешает слепой повтор.

Внешние изменения через другие приложения **не импортируются автоматически**.
Неизвестная разница не объявляется прибылью. Владелец может классифицировать
подтверждённый внешний денежный поток с уникальным ID, фактическим временем и
обоснованием:

```sh
bash scripts/trader.sh cashflow record --id ВАШ_UUID --amount 1000 \
  --at 2026-10-26T10:00:00Z --reason 'Внешнее виртуальное пополнение'
```

Сумма должна точно объяснять разницу денег, а позиции должны совпадать с
журналом. Отрицательная сумма означает внешнее списание; функции вывода средств
эта команда не предоставляет. Классификация не предназначена для маскировки
комиссий, налогов или торговых убытков. Работа с внешними сделками, переводами
бумаг, дивидендами и корпоративными действиями требует отдельного импорта;
на выделенном Sandbox-счёте их следует избегать.

## Капитал и Risk Engine

```sh
bash scripts/trader.sh equity sample
bash scripts/trader.sh equity history --limit 10
bash scripts/trader.sh risk-check --action BUY --instrument SBER:TQBR --lots 1
```

`risk-check` — ручное предложение владельца для проверки без ИИ и без заявки;
оно сохраняется с `provider=manual_check`. Отдельное исполнение возможно лишь
с явным `orders execute --sandbox-test` и количеством ровно один лот.

Каждый анализ, предторговая проверка и завершённая сверка сохраняют замер.
До пополнения положительного счёта и при включении торговли также сохраняется
база. Первое пополнение пустого счёта считается начальным капиталом, до начала
наблюдений; первую нулевую оценку пустого счёта сохранить нельзя.

`current_nano` — фактическая оценка брокера; `adjusted_current_nano` — оценка
минус записанные внешние потоки после начала наблюдений. Показатели потерь и
просадки используют скорректированный ряд. Дневная база — первый замер дня по
Москве (UTC+3), high-water — максимум замеров, не меньше исходных 100 000 ₽.
Это выборочные наблюдения, не непрерывный контроль и не восстановление данных
до первого замера. Доходность здесь не является полноценной unitized/TWR-метрикой.

Лимиты: позиция до 20 000 ₽, до 5 позиций, дневной убыток >=3% останавливает
покупки до следующего московского дня; наблюдавшаяся просадка >=15% фиксирует
остановку покупок по счёту. Восстановление оценки не сбрасывает остановку.
SELL свободных акций для уменьшения риска остаётся возможным. Сброса стопов нет.
Плечо, шорты, деривативы и неподдерживаемые активы запрещены кодом.

Проверяются свободные рубли с комиссией, свободные акции, лотность, размеры
позиций, согласованность портфеля, расписание, статус API, свежесть данных,
видимый объём в стакане и переполнение денежных значений. Наличие активных
заявок блокирует новую заявку вместо моделирования их потенциального исполнения.
Комиссия Sandbox — 5 bps (0,05%), резерв округляется вверх до копейки; запас
проскальзывания — 20 bps по умолчанию. Все расчёты целочисленные.

## Рыночный контекст и режимы инструментов

`market` читает последние биржевые цены, до 24 завершённых часовых свечей за
7 дней, стакан глубиной 5, текущий статус и расписание площадки. В запросе
свечей `limit` не передаётся из-за ограничения Sandbox; выбор последних свечей
делается локально. Расписание запрашивается с текущей даты UTC.

Площадка инструмента может иметь длинный session alias. Предпочитается точный
календарь, затем MOEX при явном `REAL_EXCHANGE_MOEX`. Пустая валюта стакана
берётся из проверенных метаданных того же RUB-share UID и помечается источником.
Незнакомые данные не угадываются. Ошибки API показывают HTTP/код/сообщение,
но токен удаляется из диагностического текста.

Сейчас поддерживается только `SECURITY_TRADING_STATUS_NORMAL_TRADING`.
Дилерская сессия `DEALER_NORMAL_TRADING` не включена; в выходные биржевая цена
может оставаться пятничной, несмотря на свежий дилерский стакан. День недели
не подменяет статус и календарь. Новости и фундаментальные показатели отсутствуют.

- `protective`: только точные пары из `PREFERRED_INSTRUMENTS`.
- `experimental`: список не ограничивает и не приоритизирует выбор; он лишь
  задаёт кандидатов по умолчанию. Через `--instruments` можно передать другие
  RUB-акции, до 50 на анализ. Автоматического поиска по всему рынку пока нет.

Режим инструментов не отменяет остальные ограничения и не включает дилерские торги.

## Провайдер ИИ

Текущий `.env` использует `AI_PROVIDER=codex_cli`. Нужен установленный Codex CLI
0.164.0 с `codex login` через ChatGPT; API-ключ OpenAI не нужен. Приложение
запускается на хосте под тем же пользователем. Auth-файлы не копируются в проект
или Docker, служебные OAuth-токены хранит сам Codex. Действуют лимиты подписки.

Codex получает только рыночный контекст через stdin, работает во временном
каталоге с read-only sandbox и JSON Schema. Shell, hooks, plugins, apps,
браузер, computer use, генерация изображений, web search и multi-agent отключены.
Личный config.toml не загружается; брокерский токен, API-ключ и пароль БД не
передаются в окружение дочернего процесса. Сохраняются финальный ответ, thread
ID и доступный usage, без промежуточных рассуждений/stderr. На Linux таймаут
завершает группу процессов. CLI может иметь собственные внутренние сетевые повторы.

Альтернатива: `AI_PROVIDER=openai_api` с локально заполненным `OPENAI_API_KEY`.
Responses API использует Structured Outputs, `store=false` и лимит ответа;
автоматических повторов платного запроса нет. Никакой провайдер не имеет
инструмента отправки заявок. ИИ не меняет риск-лимиты или записи денежных потоков.

## История

```sh
bash scripts/trader.sh history --limit 10
bash scripts/trader.sh history --id UUID_АНАЛИЗА
```

Сохраняются снимок, точный запрос, ответ, решение, результат проверки, расход
токенов и ошибки. Статус `validated_proposal` и `risk.allowed=true` означают
проверку предложения по снимку. `execution_enabled=false` в анализе по-прежнему
означает отсутствие автоматического исполнения командой analyze. Фактическая
отдельная Sandbox-заявка отражается в `sandbox_execution` / `sandbox_order_state`
и журнале `orders`, а не переключением этого флага.

## Конфигурация

`.env` имеет права 0600, исключён из Git и build context. Ключи не отправляйте
в чат. Go читает простой KEY=VALUE без shell-подстановок; окружение имеет приоритет.
Для нового развёртывания скопируйте `.env.example`, задайте токен Sandbox,
пароль PostgreSQL, создайте и пополните виртуальный счёт, затем укажите его ID.
Команды создания и чтения первого этапа сохранены: `accounts`, `account create`,
`account fund`, `balance`, `quotes`.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `TINVEST_TOKEN`, `TINVEST_ACCOUNT_ID` | — | Sandbox token и явно выбранный счёт |
| `INSTRUMENT_MODE` | `protective` | режим выбора бумаг |
| `PREFERRED_INSTRUMENTS` | `SBER:TQBR,GAZP:TQBR` | кандидаты по умолчанию |
| `REQUEST_TIMEOUT`, `QUOTE_MAX_AGE` | `15s`, `30m` | таймаут API и давность цены |
| `CANDLE_LIMIT`, `MARKET_MAX_AGE` | `24`, `60s` | число свечей и свежесть стакана/статуса |
| `RISK_SLIPPAGE_BPS` | `20` | запас цены, 0..1000 bps |
| `POSTGRES_USER`, `POSTGRES_DB` | `ai_trader` | локальная БД |
| `POSTGRES_PASSWORD` | — | пароль БД; уже сгенерирован локально |
| `DATABASE_URL` | — | полный DSN, переопределяет остальные настройки подключения |
| `AI_PROVIDER` | `openai_api` в коде, `codex_cli` в .env | провайдер |
| `CODEX_BINARY`, `CODEX_MODEL` | `codex`, пусто | CLI и необязательная модель |
| `CODEX_TIMEOUT` | `180s` | таймаут CLI |
| `AI_DAILY_CALL_LIMIT` | `2` | попытки модели на московский день, 1..100 |
| `AI_CACHE_TTL` | `10m` | повторное использование идентичного контекста, до 10 минут |
| `AI_MAX_INPUT_BYTES` | `32768` | предел компактного входа, 1024..262144 байт |
| `OPENAI_API_KEY`, `OPENAI_MODEL` | —, `gpt-6-luna` | только для API-провайдера |
| `OPENAI_TIMEOUT`, `OPENAI_MAX_OUTPUT_TOKENS` | `90s`, `2048` | параметры API |

Launcher по умолчанию использует Unix-сокет. Альтернативы через переменную
окружения `AI_TRADER_DB_ROUTE=published` или `bridge` сохранены для Linux Docker
Engine; published использует loopback `POSTGRES_PORT` (54329), bridge определяет
IP контейнера. Эта переменная читается shell-скриптом, а не из `.env`. Внутри
Compose приложение использует `postgres:5432`. Полный DATABASE_URL имеет приоритет.

TLS проверяется. Dockerfile загружает официальные CA Т-Банка по HTTPS,
проверяет PEM и формирует bundle; хранилище хоста не меняется. Смена пароля
POSTGRES_PASSWORD в `.env` не меняет пароль уже инициализированной БД.

## Тестирование и фактический статус

```sh
docker compose --profile test run --rm --build tests
```

Тестовая PostgreSQL отдельная, данные в tmpfs; токены брокера и Codex не
передаются. Тесты включают race detector, проверки риска, денежных границ,
коррекции доходности, сериализации счёта, транзакционных барьеров, журналов,
повторной миграции, одного UUID на решение, таймаута POST, потери подтверждения,
частичного исполнения, отмены и запрета повторного POST при неизвестном исходе.
В v5 также добавлены тесты компактного контекста, отсутствия вызова при закрытом
рынке/паузе, сохранения уменьшающей продажи после стопа покупки, повторного
использования, конкурентного дневного лимита и сохранения попытки окна.
Для CLI используются подставные исполняемые файлы и HTTP-серверы; настоящие
заявки при тестах не создаются.

26 октября 2026 полный набор Go/PostgreSQL-тестов прошёл в Docker с race detector.
Фактически выполнены Sandbox BUY/SELL, проверены комиссии, FIFO, повтор команд
и восстановление учёта. Для автоматизации добавлены интеграционные проверки
BUY → SELL с настоящей PostgreSQL и двойником брокера, восстановления готового
результата/намерения, потери ответа, выключенного автоисполнения и экстренной
паузы. Длительная автономная работа остаётся предметом наблюдения.
