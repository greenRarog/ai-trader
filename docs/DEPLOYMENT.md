# Эксплуатация: аналитика, Telegram, службы и резервные копии

Подробное описание предыдущих этапов сохранено целиком в [OPERATIONS.md](OPERATIONS.md).
Ниже — эксплуатация v6–v7. При `AUTOMATION_EXECUTE_ORDERS=true` автоматизация
исполняет свои свежие BUY/SELL в Sandbox. По умолчанию настройка выключена.
Никакие скрипты не снимают существующую торговую паузу.

Ежедневная инструкция: [DAILY_CHECK.md](DAILY_CHECK.md). Установщик также добавляет
ежедневный отчёт по `DAILY_REPORT_TIME_MSK` (по умолчанию 21:15 МСК);
файлы находятся в `.reports/` и исключены из Git. В текущем сокращённом режиме
отчёт запускается в 15:00, резервная копия — в 14:50.

## Обновить существующую установку

```bash
docker compose --profile test run --rm --build tests
bash scripts/build-local.sh
docker compose up -d --wait postgres
bash scripts/trader.sh db migrate
bash scripts/trader.sh trading status
bash scripts/trader.sh report --days 30
```

Повторно создавать или пополнять счёт не нужно. Новые параметры из `.env.example`
можно добавить в свой `.env`; не заменяйте им уже настроенный файл с секретами.
После обновления бинарника перезапустите уже установленную службу:
`systemctl --user restart ai-trader.service`.

## Аналитика без вызовов ИИ

```bash
bash scripts/trader.sh report --days 30
bash scripts/trader.sh usage --days 7
```

`report` читает согласованный снимок локальной БД. Новые котировки не запрашиваются;
время последнего наблюдения указано явно. Деньги выводятся точными десятичными
строками в рублях, доходность/просадка — в процентах. При отсутствии наблюдений
показатели капитала неизвестны, а не равны придуманной нулевой доходности.

- Прибыль портфеля: изменение оценки минус **записанные** внешние денежные потоки
  между первым и последним использованными наблюдениями.
- Доходность простая, относительно капитала в начале интервала. Это не TWR/IRR;
  при значительных вводах/выводах она ограниченно пригодна для сравнения стратегий.
- Просадка вычисляется по сохранённым наблюдениям с удалёнными внешними потоками.
- Реализованный результат считается FIFO. В стоимость покупки входит её комиссия;
  поступления от продажи уже уменьшены на комиссию. Повторно комиссии не вычитаются.
- Показаны подтверждённые исполненные заявки, комиссии, оборот, продажи с
  известной себестоимостью и оставшаяся себестоимость открытых бумаг.
- FIFO восстанавливается по всей локальной истории, даже если покупка была до
  выбранного периода. Дата относится к созданию заявки: точные времена отдельных
  частичных исполнений пока не реконструируются. Комиссии по периодам приблизительны
  в этой части; остаются фактическими накопленными суммами брокера.
- Неизвестная себестоимость, незавершённое пополнение/исполнение или известное
  расхождение учёта помечаются; итоговый FIFO при неполной истории не публикуется.
  При известных проблемах сверки не публикуется и итоговая доходность портфеля.
- Стоимость оставшихся бумаг — себестоимость, не текущая рыночная оценка.

Налоги, внешние сделки, дивиденды, корпоративные события, TWR, пассивные ориентиры
и виртуальная фиксация прибыли ещё не реализованы. `usage` показывает reported
токены; денежную стоимость подписки ChatGPT из токенов не вычисляет.

## Telegram

Создайте бота через BotFather и напишите ему `/start`. Bot API должен иметь право
писать в указанный чат. В локальном `.env` задайте:

```dotenv
TELEGRAM_ENABLED=true
TELEGRAM_BOT_TOKEN=YOUR_BOT_TOKEN
TELEGRAM_CHAT_ID=YOUR_CHAT_ID
```

Не отправляйте настоящий токен в GitHub или чат разработки. Затем:

```bash
bash scripts/trader.sh notify test
bash scripts/trader.sh notify list
```

Настройки бота не передаются дочернему Codex. Отправляются только операционные
сводки: завершение анализа, состояния заявок, ручная пауза/возобновление,
остановка по наблюдаемым потерям и ошибка цикла (не чаще одной за час).
Сырые ответы брокера, ключи и содержимое `.env` в сообщения не включаются.
Ошибки доставки не меняют результат торговой операции.

Очередь хранится в PostgreSQL с уникальным ключом события. Перед отправкой запись
становится `sending`. Если процесс упал или исход HTTP неизвестен, автоматического
повтора нет: Telegram не даёт нашему запросу ключа идемпотентности. `sending` и
`unknown` требуют просмотра владельцем. Отказ 429 с `retry_after` допускает до
трёх попыток с задержкой; прочие явные отказы остаются `rejected`.

```bash
bash scripts/trader.sh notify flush
```

После изменения `.env` перезапустите уже установленную службу:
`systemctl --user restart ai-trader.service`.

Очередь также обрабатывается работающей автоматизацией раз в минуту. Старый
получатель не подменяется новым при смене `TELEGRAM_CHAT_ID`. Для нового чата
создаются новые события. У бота **нет** входящих торговых команд, команд вывода
денег и возможности менять лимиты. Контракт: [Telegram Bot API](https://core.telegram.org/bots/api#sendmessage).

## Пользовательские службы systemd

Установщик запускается под тем же пользователем, что выполнил `codex login`.
Доступ пользователя к Docker и Docker Compose обязателен.

```bash
# Только создать файлы в .state/systemd, ничего не устанавливать:
python3 scripts/install-services.py --render-only
# Установить и запустить службы пользователя:
python3 scripts/install-services.py
```

Устанавливаются:

- `ai-trader.service`: непрерывный `automation run`, перезапуск при аварийном
  завершении. Перед запуском поднимается только PostgreSQL проекта.
- `ai-trader-backup.timer`: резервная копия в `BACKUP_TIME_MSK` (по умолчанию
  03:15), без случайной задержки; пропущенное задание запускается после включения.
- `ai-trader-backup.service`: создание dump и полное тестовое восстановление.
- `ai-trader-report.timer`: отчёт в `DAILY_REPORT_TIME_MSK` (по умолчанию 21:15),
  без догоняющего запуска пропущенного отчёта на следующее утро.
- `ai-trader-report.service`: свежая сверка и сохранение ежедневного отчёта.

Файлы служб ссылаются на текущий путь репозитория и `.env`; копий секретов в них
нет. После переноса каталога повторно запустите установщик. Go на хосте не нужен.
Прокси при необходимости задайте в `.env`, чтобы они были доступны службе.

```bash
systemctl --user status ai-trader.service ai-trader-backup.timer
journalctl --user -u ai-trader.service -n 100 --no-pager
journalctl --user -u ai-trader-backup.service -n 100 --no-pager
systemctl --user list-timers ai-trader-backup.timer
```

Для запуска пользовательского manager после перезагрузки без входа в систему:
`loginctl enable-linger "$USER"`. ОС может потребовать права администратора.
Скрипт сам это системное изменение не выполняет. Docker daemon тоже должен
запускаться при старте системы.

Остановить автоматизацию и расписание копий:

```bash
systemctl --user disable --now ai-trader.service ai-trader-backup.timer
```

Остановка процесса не меняет записанную торговую паузу. Для неё есть отдельная
`bash scripts/trader.sh trading pause`. Активные заявки требуют отдельной отмены.

## Резервные копии и проверка восстановления

```bash
bash scripts/backup-db.sh --verify
# Проверить выбранный архив ещё раз:
bash scripts/check-backup.sh /absolute/path/to/ai-trader-TIMESTAMP.dump
```

Скрипт копирует именно PostgreSQL из Compose этого проекта. При явно заданном
`DATABASE_URL` он останавливается: для внешней БД нужно настроить её собственный
бэкап, чтобы не получить копию другой базы.

Dump в формате PostgreSQL custom пишется атомарно, проверяется `pg_restore --list`,
получает SHA-256 sidecar. Полная проверка восстанавливает архив в сервис
`postgres-restorecheck`: отдельная БД в tmpfs, без портов и production volumes.
Копия счёта ставится на паузу, очередь уведомлений отключается; никакой экземпляр
трейдера к этой БД не запускается. После проверки временный контейнер удаляется.
Рабочая БД не очищается и не перезаписывается.

По умолчанию архивы в `.backups/`, права новых файлов 0600, сохраняются последние
14 копий. После успешной проверки удаляются только собственные timestamped
архивы сверх лимита. Другие файлы не затрагиваются. Неуспешный архив может
остаться для диагностики; сообщение об успешной проверке тогда не выводится.

`BACKUP_DIR` и `BACKUP_KEEP` читаются из окружения скрипта. Служба systemd получает
их из `.env`; для ручного запуска можно передать переменные явно:

```bash
BACKUP_DIR=/path/to/private-backups BACKUP_KEEP=30 bash scripts/backup-db.sh --verify
```

`.env`, OAuth-файлы Codex и секреты Telegram в dump не включаются. Архивы содержат
брокерскую историю и идентификаторы: Git и Docker build их игнорируют. Хранение
на том же диске защищает от ошибок приложения, но не от потери диска; перенос
копий на отдельный носитель/защищённое хранилище нужно настроить отдельно.
Секреты сохраните отдельно средствами владельца — без них новый хост не подключится.

Для реального восстановления сначала остановите службу и зафиксируйте паузу,
проверьте архив изолированно. Разворачивайте восстановленную БД в **новом томе**,
сохраняя старый до проверки. Проверьте миграции, паузу, баланс, незавершённые
намерения и очередь уведомлений перед подключением приложения. Не используйте
слепое удаление рабочего тома или `pg_restore --clean` в рабочую БД.
Сценарий автоматического разрушительного восстановления намеренно не добавлен.

## CI

GitHub Actions запускает изолированные Go/race/PostgreSQL-тесты через Compose.
Секреты и настоящие брокерские операции для CI не нужны.


## Проверки этой версии

```bash
python3 scripts/test-ops.py
docker compose --profile test run --rm --build tests
```

Первый набор — offline-тесты атомарного архива, retention, контрольной суммы,
изоляции restore target и файлов служб с подставным Docker. Он не доказывает
фактическое восстановление PostgreSQL. Для этого нужна команда backup --verify
на хосте с Docker. Новые Go/PG-тесты и реальный restore в окружении агента
запустить нельзя из-за недоступного Docker socket; перед эксплуатацией нужен
прогон выше. Файлы systemd проверены systemd-analyze; службы в окружении агента
не установлены и не запущены.
